# Архитектурный анализ и фундаментальные проблемы симуляции Zombie AI

---

## Часть 1. Как работает проект в настоящее время

Проект представляет собой комплексную симуляцию выживания в зомби-апокалипсисе с поддержкой нейросетевого ИИ (PyTorch / PPO / GRU + генетическая эволюция), гибридного рендеринга и вычислений на Rust (PyO3/Maturin), многоуровневой генерации мира (BSP, Graph Grammar, WFC) и детализированных физико-биологических систем.

### 1.1. Архитектура ядра симуляции (`src/simulation/`)
* **`SimulationEngine` (`engine.py`)**: Главный оркестратор симуляции. Управляет циклом обновлений (tick loop), обновлением активных чанков, движением и взаимодействием сущностей, спавном (посредством `EntitySpawner`), коллизиями авто-зомби и синхронизацией времени симуляции (1 реальный час = 1 игровой месяц).
* **`EventBus` (`event_bus.py`)**: Внутренняя шина событий (`NoiseEmittedEvent`, `DamageDealtEvent`, `InfectionProgressEvent`, `ItemCollectedEvent`), связывающая ECS-системы (`AcousticSystem`, `InfectionSystem`, `ParticleSystem`) без прямой жесткой зависимости между объектами.
* **`DoubleBufferedStateExchanger` (`snapshot.py`)**: Реализует паттерн двойной буферизации снимков состояния (`WorldStateSnapshot`, `EntityStateSnapshot`) для безопасного обмена данными между потоком физики симуляции и потоком рендеринга/UI.

### 1.2. ИИ выживших и нейросети (`src/ai/`)
* **`BrainNet` (`brain_net.py`)**: Рекуррентная нейросеть на базе GRU (57 входов -> 64 скрытых юнита GRU -> 13 действий). Принимает вектор из 32 параметров состояния и 5x5 матрицу локального окружения. Поддерживает бинарный сжатый формат сохранения `.zbrain` (квантование FP16 + zlib).
* **`HierarchicalDecisionPlanner` (`hierarchical_ai.py`)**: Двухуровневый планировщик целей (`HighLevelGoal`: `SURVIVE`, `FLEE_THREAT`, `ATTACK_THREAT`, `LOOT_SUPPLIES`, `SEEK_SHELTER`, `REST_AND_HEAL`, `EXPLORE`), предотвращающий дребезг (jitter) низкоуровневых действий нейросети.
* **`GeneticEvolutionManager` (`brain_net.py`)**: Реализует элитарное скрещивание и мутацию весов `BrainNet` для эволюционного обучения выживших.
* **`SurvivorGymEnv` & `ppo_brain.py`**: Предоставляют Gymnasium-совместимую среду для RL-обучения алгоритмом PPO.

### 1.3. Генерация и структура мира (`src/world/`)
* **`WorldGenerator` (`generation.py`)**: Генератор мира, использующий NumPy-векторизацию для дорожных сеток и шумы Перлина/Симплекса для рек и биомов. Применяет BSP (Binary Space Partitioning) и Graph Grammar + Wave Function Collapse (WFC) для генерации помещений и мебели.
* **`GridProxy` (`grid.py`)**: Обертка над сеткой мира. Использует плотный 2D NumPy массив для базового слоя ($Z=0$) и разреженный пространственный хеш (`sparse_z_grid`) для вертикальных уровней ($Z > 0$ и подвалов $Z < 0$).
* **`ChunkManager` (`chunk.py`)**: Менеджер чанков (16x16 блоков) с асинхронной загрузкой через `ThreadPoolExecutor` и поддержкой состояний чанка (`UNLOADED`, `GENERATED`, `INACTIVE`, `ACTIVE`).

### 1.4. Физика, баллистика и биология сущностей (`src/entities/` и `utils/`)
* **Биология выживших**: `MetabolicBalanceSimulator` рассчитывает температуру тела, намокание одежды, ветровое охлаждение, гипо/гипертермию и риск сепсиса. `AnatomicalHealth` отслеживает анатомическое здоровье по частям тела (голова, торс, конечности), кровотечения и переломы.
* **Зомби-ИИ**: Моделирует сенсорное восприятие (слух с учетом затухания в стенах, зрение с освещенностью, нюх), роение зомби (`zombie_flock`) и поанатомический урон с ампутациями и ползанием.
* **Баллистика (`ballistics_utility.py`)**: Моделирует баллистический пошаговый луч, сопротивление воздуха, ветровой дрейф, пробитие материалов, разрушение стекол и рикошеты.

### 1.5. Гибридный модуль Python-Rust (`rust_vulkan_render/` и `src/simulation/rust_engine.py`)
* **`rust_vulkan_render` (Crate на Rust)**: Нативное расширение (PyO3), содержащее:
  1. `VulkanTileRenderer`: Высокопроизводительный байтовый рендерер сетки тайлов.
  2. `compute_zombie_flock_steering`: Векторизованный расчет алгоритмов расхождения/роения зомби.
  3. `compute_a_star_3d_path`: Алгоритм 3D A* поиска пути без лишних аллокаций.
  4. `RustEngineCore`: Прототип нативного движка симуляции на Rust.

### 1.6. Управление состоянием и предметами (`src/entities/state_manager.py`)
* **`FurnitureStateManager` & `ItemStateManager`**: Отслеживают прочность, состояние (`INTACT`, `DAMAGED`, `DESTROYED`), контейнеры и порчу предметов.
* **`LazyChunkStatePersistence`**: Хранит дельта-логи изменений для неактивных чанков и гидратирует полные объекты по требованию.

## Часть 2. 5 Фундаментальных и Архитектурных Проблем

### Проблема 1: Наличие "двойственной логики" и узкие места гибридного моста Python-Rust (Python-Rust Hybrid Bottleneck & Dual State Split)

#### Суть проблемы:
Архитектурное видение проекта предполагает вынос тяжелых вычислений и симуляции в Rust, оставляя Python только для PyTorch ИИ. Однако на текущий момент симуляция находится в состоянии **незавершенной дуальной архитектуры**:
1. **Дублирование состояний**: В Rust-модуле `RustEngineCore` создана изолированная структура со своими координатами выжившего, голодом, жаждой и тиками (`survivor_x`, `survivor_y`, `survivor_health`), которая **не синхронизирована** с настоящими объектами `SurvivorEntity` и `WorldGenerator` в Python.
2. **Накладные расходы CPython C-API / PyO3**: Вызовы функций `compute_zombie_flock_steering` и `compute_a_star_3d_path` требуют постоянной упаковки и распаковки данных из Python-списков (`Vec<f32>`, `Vec<u8>`) через GIL на каждом тике симуляции. Вместо использования единой разделяемой памяти (Shared Memory / `PyBuffer` / Arrow) происходит копирование массивов координатного вектора сотен зомби.
3. **Фрагментация поиска пути**: Если Rust-версия A* возвращает пустой путь или встречает нетипичный блокирующий тайл, симуляция откатывается на медленный Python-фоллбек с созданием тысяч Python-кортежей `(f, g, x, y, z)` в `heapq`, что вызывает катастрофическое проседание FPS.

---

### Проблема 2: Жесткие ограничения архитектуры нейросети BrainNet и барьер производительности вывода (Neural Architecture & BrainNet Decision Bottlenecks)

#### Суть проблемы:
1. **Жестко фиксированный сенсорный вектор (57 входов)**: Входной вектор `BrainNet` состоит из 32 параметров статуса/ближайших сущностей и локальной сетки 5x5. Если симуляции требуется передать информацию о погоде (ветер, дождь), уровне шума, намокании одежды, наличии техники или типе пола, размерность вектора ломается, требуя переобучения всех моделей с нуля. При этом локальный сенсор 5x5 слишком мал для навигации в помещениях (выживший "не видит" стену за пределами 2 тайлов).
2. **Неэффективный цикл вывода (Inference Overhead)**: В `BrainNet.get_action_and_movement` вызов `forward` выполняется в единичных инференсах на CPU/GPU для каждого выжившего отдельно (`unsqueeze(0)`, `squeeze(0)`, `.cpu().numpy()`). Пересылки одиночных тензоров между CPU и GPU синхронизируют поток и сводят на нет параллелизм CUDA.
3. **Дискретизация действий и смешивание пространств параметров**: Модель выдает 13 выходов, где `out_arr[0]` и `out_arr[1]` обрабатываются через `tanh` для смещения `(dx, dy)`, а `out_arr[2:]` — через `argmax` для выбора дискретного действия. Подобное совмещение непрерывного управления движением и дискретного выбора действия в одной базовой линейной голове `fc_out` создает сильный градиентный шум при обучении генетическим алгоритмом или PPO.

---

### Проблема 3: Рассинхронизация менеджеров состояний и неатомарная гидратация чанков (State Synchronization & Lazy Chunk Inflation Divergence)

#### Суть проблемы:
В проекте параллельно существуют три некоординированных источника истины для состояний предметов и мебели:
1. `FurnitureStateManager` и `ItemStateManager` хранят глобальные словари `states` по координатам `(x, y, z)` и ссылкам на сущности.
2. `ChunkManager` выгружает и загружает тайловую сетку 16x16.
3. `LazyChunkStatePersistence` записывает дельта-логи изменений (`_delta_logs`).

#### В чем проявляется деструктивный эффект:
* **Утечки памяти и "фантомные" предметы**: При разрушении мебели зомби или уничтожении предмета сущность удаляется из игрового мира, но может остаться в глобальном `FurnitureStateManager.states` или `ExtendedItemState`.
* **Отсутствие атомарности (Race Conditions)**: Когда выживший перемещается через границу чанка, `ChunkManager` переводит чанк из `ACTIVE` в `INACTIVE`/`UNLOADED`. Если в этот момент выживший или зомби взаимодействуют с контейнером в выгружаемом чанке, `LazyChunkStatePersistence` сохраняет дельту, но глобальный `FurnitureStateManager` оставляет старое состояние. При повторной загрузке чанка дельта накладывается повторно, приводя к дюпу (дублированию) лута или сбросу прочности дверей.

---

### Проблема 4: Синхронная шина событий EventBus и блокировки GIL при масштабировании симуляции (Synchronous EventBus & Threading GIL Bottlenecks)

#### Суть проблемы:
1. **Синхронная обработка событий на главном тике**: `EventBus.publish()` сразу же вызывает всех зарегистрированных слушателей в том же потоке. Когда в симуляции происходит взрыв, громкий выстрел или орда зомби ломает стены, генерируются десятки `NoiseEmittedEvent` и `DamageDealtEvent`. Это приводит к каскадным вызовам `AcousticSystem`, `InfectionSystem` и `ParticleSystem` внутри текущего тика, превращая шаг симуляции в монолитный последовательный стек вызовов.
2. **Ограничение GIL в Python-многопоточности**: Хотя `ChunkManager` использует `ThreadPoolExecutor` для асинхронной генерации чанков, из-за Global Interpreter Lock (GIL) вычисления шум-карт и генерация графов помещений на Python задерживают выполнение главного потока симуляции.
3. **Неоптимизированные пространственные запросы**: Проверка видимости и звукового затухания сквозь стены (`check_line_of_sight`, `AcousticSystem`) производит физические лучи (raycasting) индивидуально для каждого зомби и выжившего, без использования общего spatial hashing сетки или вектора зеркал.

---

### Проблема 5: Монолитный God-Object `SimulationEngine` и размытие ECS-границ (Monolithic SimulationEngine & God-Object Anti-Pattern)

#### Суть проблемы:
Класс `SimulationEngine` (`src/simulation/engine.py`) нарушает принцип единственной ответственности (Single Responsibility Principle):
* Он одновременно отвечает за:
  1. Главный цикл времени и расписание тиков (Tick loop & Time scaling).
  2. Спавн и уничтожение всех сущностей (`EntitySpawner`).
  3. Вычисление физики столкновений автомобилей и зомби.
  4. Обновление состояний ИИ, метаболизма выживших и сенсоров зомби.
  5. Оркестрацию погоды, освещения и смены сезонов.
  6. Управление чанками и синхронизацию состояния.
  7. Подготовку двойного буфера снимков для рендеринга (`DoubleBufferedStateExchanger`).

#### Последствия для архитектуры:
* Любое изменение в логике ИИ, баллистике или генерации требует правки `engine.py`.
* Попытка покрыть `SimulationEngine` изолированными модульными тестами (Unit Tests) становится крайне сложной из-за жесткой связности (tight coupling) со всеми подсистемами сразу.
* Архитектура ECS (Entity Component System) оказывается "полураспадающейся": компоненты сущностей соединены прямыми ссылками на объекты вместо использования чистых систем с непрерывными массивами данных (Data-Oriented Design).

## Часть 3. Сводная таблица архитектурных проблем

| # | Проблема | Локализация | Последствия | Приоритетное решение |
|---|---|---|---|---|
| **1** | Дублирование состояния и узкие места моста Python-Rust | `rust_vulkan_render/`, `rust_engine.py` | Потеря производительности на C-API копировании, рассинхронизация параметров симуляции. | Перевод всего Loop симуляции и состояния сетки/сущностей в Rust, передача в Python только Zero-Copy PyArrow/NumPy тензоров. |
| **2** | Фиксированный вектор 57 и неэффективный инференс `BrainNet` | `src/ai/brain_net.py`, `brain_actions.py` | Сложнее добавлять новые механики, падение FPS при штучном инференсе нейросетей на GPU/CPU. | Переход на динамический/векторизованный BMM (Batched Matrix Multiplication) инференс и расширение сенсорного поля. |
| **3** | Неатомарность состояния чанков и рассинхрон `StateManager` | `state_manager.py`, `chunk.py` | Дюп предметов, фантомная мебель, утечки памяти при выгрузке чанков. | Связывание жизни `FurnitureState` и `ItemState` с владельцем-чанком и транзакционная дельта-гидратация. |
| **4** | Синхронная шина событий `EventBus` и блокировка GIL | `event_bus.py`, `systems.py` | Микрозависания (stuttering) при массовых событиях (звуки, взрывы, урон). | Асинхронная очередь событий с батчингом (Ring Buffer) и перенос тяжелых систем в Rust worker threads. |
| **5** | Монолитный `SimulationEngine` (God Object) | `src/simulation/engine.py` | Высокая связность кода, невозможность изолированного тестирования систем. | Декомпозиция `SimulationEngine` на изолированные подсистемы через сугубо компонентный подход (Data-Oriented ECS). |
